# Patch load (editor v1.62)

How the original editor computes the "Poly/Mono area load" and "Poly/Mono area memory" meters, and its "patch too
big" checks. Port: `core/include/g2/patch_load.hpp`, `core/src/patch_load.cpp`, table
`core/src/patch_load_data.cpp` (generated by `tools/patchload/gen_table.py` from `data/modules.json`). Verified
bit-exact against the original code run in an emulator (`tools/patchload/emulate.py`, §6).

The namespace is `g2::patchload`, not `g2::load`: `g2::load()` is already the file loader in `patch.hpp`.

## 1. Summary

* One `CPatchLoad` per `CPatch` (`CPatch+0x50`, built in `CPatch::CPatch` 000d96d4/000d9d44).
* It keeps, per area (EContext 0 FX, 1 VA, 2 patch settings), **a local sum** of the `_k<Name>ModuleSize` tables
  of the area's modules plus 3 words of dynamic RAM per cable, and **the last figures the synth reported** (USB
  molecule `72`) with a "reported" flag.
* Every getter returns the reported figures if the flag is set, else the local sum. Any module/cable/uprate change
  clears the flag; `CPatch::CleanDirtyData` then sends `71` (VA first, then FX) and the reply sets it again.
* **The meters only show reported figures**: `CTBWindow::SetupLoadMeter` @00129c84 writes `--` and 0 when
  `IsLoadReported(area)` is false. So offline the original shows nothing; the local sum is an estimate it falls back
  to internally. G2fresh can show it offline, labelled as an estimate.
* **Voices are not involved.** No voice count appears anywhere in `CPatchLoad`; the VA figures are those of a single
  voice instance (the synth reports them the same way: one `72` for VA, one for FX). How many voices actually fit is
  decided by the synth and reported separately (`05` CMNumberOfVoicesDump, assigned voices per slot).
* The only offline decisions the editor takes from the local sum are the **dynamic-RAM checks** (§5).

## 2. SModuleResourceSpec (0x20 bytes)

Same layout for a module table (`_k<Name>ModuleSize`, `SModuleInfo+0x14`, copied to `CBuildModule+0xC`;
`CModule::GetModuleResourceSpec` @000aa378 returns `builder+0xC`), an area sum and a synth report.

| Off | Type | Field | `modules.json` | Limit (`CPatchLoad::kMax*`) |
|----:|------|-------|----------------|-----------------------------|
| 0x00 | u16 | cycles, A code (audio rate) | s16[0] | kMaxCyc 1371 per sample |
| 0x02 | u16 | cycles, B code (control rate, every 4th sample) | s16[1] | weight 0.25 |
| 0x04 | u8 | "ZP" memory | s16[2] & 0xFF | kMaxZmem 128 |
| 0x05 | u8 | unknown; set in 22 tables (e.g. Morph 80, MixFader 80, Sw8-1 59), reported by the synth, **never summed or read** | s16[2] >> 8 | – |
| 0x06 | u16 | unused (Clear zeroes it; only Automate's table has 1) | s16[3] | – |
| 0x08/0x0A/0x0C | u16 ×3 | X/Y/P memory, A code | s16[4..6] | kMaxXmem 4336, kMaxYmem 2992, kMaxPmem 6498 |
| 0x0E/0x10/0x12 | u16 ×3 | X/Y/P memory, B code | s16[7..9] | (summed with A) |
| 0x14 | u32 | dynamic RAM | s32[0] | kMaxDynMem 131072 (0x20000) |
| 0x18 | u32 | Q memory | s32[1] | kMaxQmem 260096 |
| 0x1C | u32 | R memory | s32[2] | kMaxRmem 256 |

`HasBCode` @000a9e24 = any of B cycles / B X/Y/P non-zero. `operator+=`/`-=` @000ed18c/000ed21a wrap at the field
widths (byte +5 excluded). The Name bar (type 126, `CBModuleName` @000bb4e2) uses `_kNameModuleSize` = all zero but
71 words of RAM; `modules.json` has no record for it, so the generator adds it.

The tables look partly unfinished: many modules have 0 cycles and only ZP 1 (OscC, Reverb, all delays, LfoC…),
many have X/Y/P = 1,1,1,1,1,1, no delay uses Q memory. The editor's local estimate is therefore much lower than what
the synth would report for real patches; that is probably why the meters wait for the synth.

## 3. Algorithm (CPatchLoad, 000ed144..000eeaae)

Object layout: +0 u16 module count, +2 u16 cable count, +4/+8/+0xC float critical % (FX/VA/settings), +0x10/+0x14/
+0x18 critical type, +0x1C/+0x3C/+0x5C local sums FX/VA/settings, +0x7C/+0x9C/+0xBC reported FX/VA/settings,
+0xDC/+0xDD/+0xDE reported flags.

* `AddModule(CModule*)` @000ee98a (`CPatch::InternalNewModule` @000dbc52, from module new/dump molecules, i.e. also
  when a patch is loaded): area = `CModule+0x34`; spec = the type's table; **if `CModule+0x40` (bandwidth) == 1
  (uprated), fold B into A**: cyclesA += cyclesB, X/Y/P A += X/Y/P B, B fields = 0 (same as
  `B2AConvertResourceSpec` @000ed306). Add to the area sum (ZP: low byte only; byte +5 not added), then
  `UpdateCriticalResource(area)`. `RemoveModule` @000eeaae subtracts. Uprate change (`HandleModuleABCode` @000dcf0e)
  = remove, change, add.
* `AddCable(ctx)` @000ee544 / `RemoveCable` @000ee50a: area dynamic RAM ±3 (per cable segment; `HandleCableDump`
  @000ddd2c calls it once per cable of the file's cable list).
* Patch-settings pseudo-modules are created by `CPatchToolbarData::AddModule` @000e9ef4, which does **not** call
  `AddModuleToPatchLoad`: area 2 stays zero.
* `UpdateCriticalResource(ctx)` @000ee488: clears the reported flag, `CalculateCriticalResource` →
  float at +4/+8 (the settings result also lands at +4, a harmless bug).

Percentages (all `float`, computed in double by SSE2 and rounded to float; the port is bit-identical):

```
cycles = float(((double)A + (double)B * 0.25) * 100.0 / 1371.0)       GetCycles @000ed522
x      = float((double)(xA + xB) * 100.0 / 4336.0)                     GetXmem   @000ed5ba
y      = float((double)(yA + yB) * 100.0 / 2992.0)                     GetYmem   @000ed63e
p      = float((double)(pA + pB) * 100.0 / 6498.0)                     GetPmem   @000ed6c2
zp     = float((double)zp * 100.0 * 0.0078125)                         GetZPmem  @000ed746
ram    = float((double)dynRam * 100.0) * 7.62939453125e-06f   (1/131072)  GetRAM  @000ed7c4
q      = float((double)q * 100.0) / 260096.0f                          GetQmem   @000ed874
r      = float((double)r * 100.0) * 0.00390625f               (1/256)  GetRmem   @000ed924
```

(B cycles count a quarter: the B code is the control-rate code, run once per 4 samples; uprating runs it every
sample. Verhue's guess, `A/1372 + B/5000`, is wrong.) `CalcModuleCyclePercent` @000ed468 is the same formula on one
module's table.

`FindCriticalResourceType` @000ede6c: **cycles are not candidates**. best = X (type 1); Y (2) if Y > X; then P (3),
ZP (4), RAM (5), Q (6), R (7), each only if strictly larger. `CalculateCriticalResource` @000ee0c8 returns that
resource's %. An area that never received a module or cable keeps the constructor's type 0 and 0 %.

Meters (`CTBWindow::SetupLoadMeter` @00129c84, VA meters at `CTBWindow+0x3A4`/`+0x43C`, FX at `+0x3F0`/`+0x488`):
"load" = `GetCycles(area)`, "memory" = `GetCriticalResource(area)`; text `Utils::FloatToStr(v, 1)`, bar
`(uchar)(int)v`, green if ≤ 100 else red. In practice ZP is the critical resource for 88 % of VA areas of the corpus.

## 4. Synth report (molecule 72, `CMPatchLoad::ReadStream` @000163da)

`u8 area (≠0 = VA)`, then the spec: u14 cyclesA, u14 cyclesB, u8 ZP, u14 → byte +5, 6 × u14 X/Y/P A/B, u14 dynamic
RAM, u16 hi + u16 lo Q, u14 R (28 bytes). `CPatch::HandlePatchLoad` → `SetDspReportedLoad` @000ee320 copies it to
+0x7C/+0x9C, sets the flag, recomputes the critical resource; the same getters apply. Verhue's 4315/260000 limits
are approximations of kMaxXmem/kMaxQmem. Port: `parseReport`, `fromReports` (u14 decoding per usb-protocol.md, not
checked against hardware).

## 5. Offline checks ("patch too big")

`GetFreeDynamicRam` @000ed144 = 0x20000 − RAM(FX) − RAM(VA) − RAM(settings = 0), an `int`, always from the local sums.
Callers compare it as unsigned:

* `CTabButton::Action` @0012698e (add a module from the toolbar): allowed if the type's RAM ≤ free.
  `InternalNewModule` also throws `XPToMany` for a 128th module in an area.
* `CCableDragDropManager::Drop` @00019514 (new cable): allowed if free > 2.
* `CClipboard::AdaptForNewModules` @0014ca0e (paste): `CPatchData::GetDynamicSize` @000e56a0 = 16-bit sum of
  3 per cable segment + low 16 bits of each module's RAM (uprate ignored); the paste is dropped if free < size.

Port: `canAddModule`, `canAddCable`, `dynamicSize`, `canPaste`. The tightest real patch of the corpus still has
27854 words free, so these checks practically never fire.

## 6. Verification

`tools/patchload/emulate.py` maps `original/mac/G2Editor_i386` in unicorn, builds a `CPatchLoad` with its
constructor, feeds each patch's modules (fake `CModule`: builder→real `_k<Name>ModuleSize`, context, bandwidth) and
cables to the original `AddModule`/`AddCable`, and calls the original getters. `tests/golden/patch_load.tsv` holds
the results for the committed corpus (11 patches + Verhue's sample); `tests/test_patch_load.cpp` checks the port
bit-exactly against it. Over `corpus-external` (5 578 files, 8 869 patches including performance slots, 17 732
area rows) the port and the emulated original agree on every sum, every percentage (bit-exact), every critical type
and every free-RAM value; only 3 files that `pch2dump.py` cannot decode were not compared.

## 7. Open questions (synth side only)

* What the synth reports for a patch, and how far it differs from the editor's local estimate (stubbed tables).
  Needs a capture of `72` replies from hardware.
* Meaning of byte +5 (reported, unused by the editor) and of "ZP", "Q", "R" in DSP terms.
* Voice allocation: how many voices the synth assigns for a given VA load (4 DSPs?), only observable via `05`.
